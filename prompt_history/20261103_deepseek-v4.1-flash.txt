## 2. 推奨アーキテクチャ

**A. ローカル Windows オーケストレータ（推奨・低リスク）**

`tools/build-wsl-image.ps1` が全体を駆動し、Linux 側の処理は `provision.sh` / `cleanup.sh` に分離。

```mermaid
flowchart LR
  A[preflight<br>notes/tag/version/disk] --> B[download Ubuntu rootfs<br>+SHA256SUMS検証]
  B --> C[wsl --import<br>homepage-v2-build]
  C --> D[provision.sh<br>-u root]
  D --> E[fetch-app.sh --fresh --dist]
  E --> F[cleanup.sh]
  F --> G[manifest.json 埋込]
  G --> H[wsl --export → pigz → sha256]
  H --> I[verify: import → start.sh → HTTP 200]
  I --> J[gh release create --latest --target SHA]
```

ポイント:

- **`wsl --install` を使わない。** `https://cloud-images.ubuntu.com/wsl/noble/current/ubuntu-noble-wsl-amd64-wsl.rootfs.tar.gz` を取得（`SHA256SUMS` で検証）→ `wsl --import homepage-v2-build D:\wsl_backup\build <tar>` → `-u root` で `useradd -m -s /bin/bash ubuntu`。これで**対話ゼロ・既存 Ubuntu を汚さない・再実行可能**になります。
- **プロビジョニングは `-lc "..."` に長文を埋め込まない。** `D:\wsl_backup\build\provision.sh`（LF, UTF-8 BOMなし）に置き `wsl -d homepage-v2-build -u root -- bash /mnt/d/wsl_backup/build/provision.sh`。引用符・CRLF 事故（メモの既知バグ）を構造的に消せます。
- `-d` に引用符を付けない（メモの `WSL_E_DISTRO_NOT_FOUND`）。
- Docker は `/etc/wsl.conf` に `[boot]\nsystemd=true` を書いて `wsl --terminate` → 再起動してから `systemctl enable --now docker`。現行 doc の `systemctl enable` は systemd 無効だと失敗するので、ここは明示的に直すべき箇所です。
- **`wsl --shutdown` は使わない**（他の distro を巻き込む）。`wsl --terminate <name>` のみ。

**B. Dockerfile で rootfs を作る（CI 化したい場合）**

Ubuntu コンテナで同一 `provision.sh` を走らせ `docker export` → gzip。Linux ランナーでビルドでき、レイヤキャッシュ・`trivy` スキャン・SBOM が素直に載ります。ただし `/etc/wsl.conf`、systemd、interop まわりを手で足す必要があり、**成果物の同一性は A ほど保証されない**。まず A を作り、`provision.sh` を共有資産にして後から B を追加するのが安全です。

## 3. リリースノート運用（置き場所の提案）

`D:\wsl_backup\homepage-release-notes-v<version>.md` を AI が事前生成、というのはそのままで良いですが、**バージョンの決定権はスクリプト側に持たせる**のが要点です。

1. `-Version v2.1.1` か、ファイル名から抽出（複数あれば最新 semver）。
2. **長いビルドの前に fail-fast**:
   - notes ファイルが存在するか
   - `https://raw.githubusercontent.com/okamoto53515606/homepage/main/package.json` の `version` と一致するか（`NEXT_PUBLIC_APP_VERSION` はビルド時に焼き込まれるため、ズレたら画面だけ古い版になる）
   - `gh release view v2.1.1` でタグ未作成か
   - 空き容量（tar 中間 + tar.gz で 15GB 程度）
3. ビルド完了時に `git -C ~/homepage rev-parse HEAD` を取得し、`gh release create ... --target <SHA>` で**ビルドしたコミットにタグを打つ**（main が進んでも版と中身がズレない）。
4. アセット名は `homepage-v2-latest.tar.gz` / `.sha256` 固定（インストーラの URL と一致必須）、`--latest` 必須。
5. notes は `--notes-file` で本文に。ビルドログ（所要時間・サイズ・各ツール版・base rootfs 版・HEAD SHA）は別ファイルで添付すると、後の「この不具合どのイメージ？」が一撃で分かります。

## 4. 軽量化・脆弱性対応の具体策

**やるべき追加**

- `apt-get update && apt-get -y full-upgrade`（`upgrade` ではなく `full-upgrade`）。`upgrade` は依存変更を伴うセキュリティ修正を取りこぼすことがあります。
- `apt-get install --no-install-recommends`（推奨パッケージで数百MB削れる）。ただし `docker-ce` 等は推奨に依存するので個別に確認。
- ベース rootfs を `current` ではなく**日付入りリリースで固定**し、版を manifest に記録（再現性）。
- `trivy rootfs` を WSL 内で実行し、CRITICAL で fail（任意）。`dpkg-query -W` の結果を SBOM として添付。
- イメージ内 `/etc/homepage-image.json` に build日時 / base / node / docker / aws-cli / app SHA を埋める（サポート時に効く）。

**注意点**

- **WSL カーネル自体はイメージに入りません。** 脆弱性対応として `wsl --update`（ホスト側）をリリースチェックリストに明記。Ubuntu は noble（24.04 LTS, 2029まで）継続で問題なし。
- `unattended-upgrades` の purge は妥当（再現性優先）。ただし**purge は最後**、`full-upgrade` より前だと意味が消えます。
- `/usr/share/doc` の削除は `copyright` 以外を消す現行方針でOK。`/var/lib/apt/lists/*` 削除も問題なし。
- `/var/log` は現行の `cp /dev/null`（inode 維持）が正解。`rm` にしないでください。
- **Docker の `/var/lib/docker` を丸ごと消すのは非推奨**（初回起動で再初期化に時間がかかる）。`docker system prune -a --volumes -f` で十分。
- 個人情報ゲートを cleanup に追加：`~/.bash_history`, `/root/.bash_history`, `~/.aws`, `~/.npmrc`, `~/.docker/config.json`, `~/.git-credentials`, `~/.sudo_as_admin_successful` を削除し、`~/homepage/.env` に `AKIA|SECRET|TOKEN` が無いことを grep で確認（`env_template.txt` 由来なので通常ヒットしない）。ここは**リリース前の最後の関門**として自動化する価値が高いです。

## 5. リリース前ゲート（これを入れると事故がほぼ消える）

1. `gzip -t` でアーカイブ健全性、sha256 ファイルが**1行・先頭64桁**であること（`installer` の読み取り仕様に一致）
2. サイズ < 2 GiB（GitHub の単一アセット上限）
3. **本番と同じ手順で import 検証**: `wsl --import homepage-v2-verify ...` → `docker info` / `node -v` / `aws --version` / `test -d ~/homepage/setup/.next` → `start.sh` を起動し `http://localhost:3001/setup0` が 200 になるまで最大10分ポーリング → `--terminate` → `--unregister`
4. `.next` 内に焼き込まれたバージョン文字列が期待値と一致（`grep -rl "$VER" ~/homepage/setup/.next`）
5. 既存の `tools/test-update-wsl-app.ps1 -DistroName homepage-v2-verify` を流して更新系の回帰も同時に確認

## 6. CI に載せる場合の注意

GitHub ホストの Windows ランナーは**ネスト仮想化が前提の WSL2 が安定して動きません**（`wsl --install` も不可）。`gh release` だけをランナーでやるのは可能ですが、ビルドはセルフホスト Windows ランナーか手元実行が現実的です。Dockerfile 方式（案B）にすればビルド自体は Linux ランナーに移せますが、**import/起動検証だけは Windows が必要**という制約は残ります。

## 何が起きていたか

`gh release view v2.1.2` は「まだタグが無い」ことを **stderr に `release not found` と書いて終了コード 1** で知らせます。これは正常系ですが、PowerShell 5.1 では

- `$ErrorActionPreference = 'Stop'` の状態で
- `*> $null`（= stderr をリダイレクト）

を組み合わせると、その stderr が **終了エラーに変換されて `trap` が発火**します。つまり「タグが無いことを確認する」という正しい動作が、致命的エラー扱いされていました。
